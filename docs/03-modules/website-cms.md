# Module: Website & CMS

> **Agent Context** — Load this block first.
> **Summary:** Gives every tenant school a dynamic public-facing website — homepage, about, principal message, departments, teachers, classes, admissions, events, news, notices, gallery, contact — managed through a CMS with dynamic sections, SEO settings, tenant branding, navigation/footer control, and custom domain binding. One theme ships initially; a theme system enables more later. Rendering/hosting architecture lives in [`website-builder.md`](../02-architecture/website-builder.md); this doc is functional.
> **Co-load with:** `../02-architecture/website-builder.md` · `../05-database/entities/website-cms.md` · `../02-architecture/multi-tenancy.md`
> **Owns entities:** `website_settings`, `themes`, `website_pages`, `page_sections`, `navigation_menus`, `news_posts`, `school_events`, `gallery_albums`, `gallery_items`, `contact_submissions`, `seo_settings`
> **Depends on modules:** admissions, communication, academics, staff-management, platform-admin

## 1. Purpose

The product is not limited to an admin dashboard (scope §11): every school operates a public website on `<slug>.<platform-domain>` or its verified custom domain. This module is the CMS behind that website — page management with dynamic sections, news/events/gallery content, an admissions page whose form feeds the admissions module, published notices from the communication module, SEO, and branding drawn from tenant settings.

The website and the admin system share tenant data across a strict security boundary: the public renderer reads only content explicitly published, via a scoped read-only machine token ([`api-architecture.md`](../02-architecture/api-architecture.md) §2.2).

## 2. Business Objective

- Make the platform a full digital presence, not just back-office software — a differentiator when selling to schools without a website.
- Drive admissions: the website is the top of the enquiry funnel; measurable via contact/admission form conversions.
- Zero-IT publishing: non-technical school staff update news, events, and pages without a developer.

## 4. Permissions

Permissions follow the RBAC model in [`auth-and-rbac.md`](../02-architecture/auth-and-rbac.md). Permission keys use `<module>.<resource>.<action>`.

| Permission key | Description | Default roles |
| -------------- | ----------- | ------------- |
| `website.page.view` | View pages/sections in the CMS | `school_admin`, `it_admin`, `principal` |
| `website.page.create` / `website.page.update` / `website.page.delete` | Manage pages and their sections | `school_admin` |
| `website.page.publish` | Publish/unpublish pages | `school_admin`, `principal` |
| `website.news-post.create` / `update` / `delete` | Manage news posts | `school_admin` |
| `website.news-post.publish` | Publish news | `school_admin`, `principal` |
| `website.school-event.create` / `update` / `publish` | Manage website events | `school_admin` |
| `website.gallery-album.create` / `update` / `publish` / `delete` | Manage galleries and items | `school_admin` |
| `website.navigation.update` | Edit header/footer menus | `school_admin`, `it_admin` |
| `website.settings.update` | Theme config, homepage assignment, publish/maintenance toggle | `it_admin`, `school_admin` |
| `website.seo.update` | Site and per-page SEO settings | `it_admin`, `school_admin` |
| `website.custom-domain.create` / `update` / `delete` | Bind/verify/remove custom domains | `it_admin`, `school_owner` |
| `website.contact-submission.view` / `update` | Read and triage contact submissions | `reception`, `school_admin` |

`website.page.view` is the CMS **read key for all website content** (pages, themes, settings, navigation, SEO, news posts, school events and gallery albums with their items): this table has no separate view key for those, and every `website.*` row above is registered in `permissions.py`. Gallery **item** writes (add, edit, delete, reorder) use `website.gallery-album.update`: §4 has no item key, because an item has no lifecycle of its own and is only ever changed as part of editing its album. `website.public-content.view` is **not** a role permission: it is the machine scope of the renderer's platform token, which will be declared in `MACHINE_SCOPES` in `core/rbac/machine.py` when the public content API ships (PR C), so no grantable `Permission` row exists for it and no role can hold it. Once PR C lands, a JWT is refused on public routes and the machine token on CMS routes.

## 5. Main Features

1. **Standard pages** — homepage, about school, principal message, departments, teachers, classes, admissions, contact (scope §11), each composed of theme-defined dynamic sections; unlimited additional custom pages.
2. **Dynamic CMS sections** — each page is an ordered list of typed sections (hero, rich text, stats, staff grid, CTA, FAQ, embedded form…) whose types the active theme declares; content is structured JSON, so themes can re-skin it later.
3. **News & events** — publishable news posts and school events with listing + detail pages; notices published by the communication module surface on the site (read-only here — cross-ref).
4. **Gallery** — albums of images/video embeds, optionally linked to events.
5. **Admissions page & forms** — admission enquiry/application form whose submissions create records in the admissions module (enquiries/applications); generic contact form stored as `contact_submissions`.
6. **Branding** — logo, colors, fonts, favicon come from tenant settings ([`multi-tenancy.md`](../02-architecture/multi-tenancy.md) §5) and are applied by the theme; no per-page branding forks.
7. **Navigation & footer** — editable header menu, footer menus, social links, contact block.
8. **SEO** — site-wide and per-content meta title/description, Open Graph image, canonical URL, robots directives, sitemap.xml and structured data emitted by the renderer.
9. **Custom domain binding** — school connects `www.myschool.tld` (CNAME + automated TLS per multi-tenancy §4); subdomain remains as fallback.
10. **Theme system** — one platform theme at launch; themes are a platform-scope catalog with declared section types and a config schema, so new themes can ship without data migration (scope §11 "WordPress-style" future).

## 6. Sub-features

- **Pages:** draft/published/archived states; publish scheduling *(recommendation)*; page duplication; slug management with redirects on rename *(recommendation)*; per-locale content for tenant languages.
- **Sections:** drag-and-drop reordering; per-section visibility toggle; live preview before publish; teacher/class/department sections can auto-populate from academics and staff-management data marked "show on website".
- **News/events:** cover images, excerpts, publish dates; events with start/end, location, all-day flag; past-event auto-archival on listings.
- **Forms:** spam protection (honeypot + rate limiting; CAPTCHA configurable *(recommendation)*); consent text configurable per tenant.
- **Custom domains:** guided DNS instructions, verification token check, TLS issuance status, primary-domain selection. The instructions say: keep the CNAME, a direct CNAME to the platform's target (CNAME chains are not followed); the TXT record can be removed after verification, but if it is kept it must keep this domain's token. The daily re-check reads the CNAME and, when a TXT record exists, requires the token, so a new owner of the domain who publishes their own token evicts a stale holder within three daily runs. A domain becomes primary only once its HTTPS certificate is issued.
- **Maintenance mode:** replace the site with a neutral notice (also forced during tenant suspension per multi-tenancy §7).

## 7. Workflows

### 7.1 Page publish

```mermaid
flowchart TD
    A[Editor creates/edits page<br/>website.page.update] --> B[Compose sections + preview]
    B --> C{Publish permission?}
    C -- has website.page.publish --> D[Published: renderer cache invalidated,<br/>sitemap regenerated]
    C -- no --> E[Submit for review → principal/admin publishes]
    D --> F[Live on subdomain / custom domain]
    D -.-> G[Unpublish / archive]
```

Steps: editor composes sections against the active theme's section catalog; preview renders through the real renderer with a draft token; publishing flips status, invalidates the edge cache, and regenerates sitemap/feeds. Review gate applies only when the editor lacks the publish permission. A published page, news post, event or album (and a published album's items) can be edited only by someone holding that resource's `.publish` key; an update-only editor gets 422 `publish_required` and works on a draft instead (unpublish first). A published page also cannot be saved with zero visible sections (422 `no_visible_sections`).

### 7.2 Custom domain binding

```mermaid
flowchart TD
    A[it_admin enters domain] --> B[Platform issues verification token<br/>+ CNAME instructions]
    B --> C{DNS verified?}
    C -- retry/failed --> B
    C -- yes --> D[Automated TLS issuance at the edge]
    D --> E[Domain active · set as primary optional]
    E -.-> F[Remove/disable domain → fallback to subdomain]
```

### 7.3 Website form submission

Visitor submits admissions/contact form → rate-limit + spam checks → contact forms create `contact_submissions`; admission forms create enquiry/application records **in the admissions module** (cross-ref [`admissions.md`](admissions.md)) → notification to `reception`/`admission_staff` → triage status tracked.

## 8. User Journeys

- **School admin:** onboarding creates the site pre-populated from wizard data → replaces placeholder homepage sections → uploads gallery from the annual day → publishes a news post; total time under an hour, no IT involvement.
- **it_admin:** binds `www.school.tld`, watches verification turn green, sets it primary; fills site-wide SEO defaults and the analytics ID.
- **Principal:** drafts the principal message with the AI assistant, edits tone, publishes.
- **Prospective parent (visitor):** lands on homepage → checks classes and fees info page → submits the admissions enquiry form → receives confirmation email; the enquiry appears in the admissions pipeline.

## 9. Inputs

- Page/section content (structured JSON per section type), rich text, uploaded media (via platform `files`, api-architecture §2.8).
- News posts, events, gallery uploads, navigation trees, SEO fields, theme configuration values.
- Custom domain names; DNS verification results (automated).
- Public form submissions (contact, admissions) — unauthenticated, validated, rate-limited.

## 10. Outputs

- Published website content served by the multi-tenant renderer ([`website-builder.md`](../02-architecture/website-builder.md)): pages, listings, detail pages, sitemap.xml, robots.txt, RSS for news *(recommendation)*.
- `contact_submissions` records; enquiry/application records handed to admissions.
- Events emitted: `website.page.published`, `website.contact-submission.created` (webhooks per api-architecture §2.6).

## 11. Validations

- Slugs unique per tenant per content type; reserved slugs (`admin`, `api`, `verify`…) blocked.
- A page cannot publish with zero visible sections; section content validated against the section type's schema.
- Only one homepage; deleting a published page requires unpublish first; navigation items must reference existing published targets or external URLs.
- Custom domain: valid FQDN, not already claimed by another tenant (global uniqueness), verification before activation.
- Uploaded media validated for type/size and AV-scanned per [`security.md`](../06-security/security.md); public forms: field-level validation, honeypot, per-IP rate limits.
- Published content must never expose non-public data: only staff/class records flagged "show on website" are readable by the renderer token.

## 16. API Requirements

Conventions per [`api-architecture.md`](../02-architecture/api-architecture.md). Two surfaces: authenticated CMS API and the read-only public content API consumed by the renderer via a scoped machine token.

- CMS, **built in PR A**: `GET/POST /api/v1/website-pages` (filters `status`, `page_type`, `search` on title and slug) · `GET/PATCH/DELETE /api/v1/website-pages/{id}` · `POST /api/v1/website-pages/{id}:publish` / `:unpublish` / `:archive` / `:preview` · `PATCH /api/v1/website-pages/{id}/page-sections` (ordered bulk replace, at most 50 sections)
- CMS, **built in PR B** (reads under `website.page.view`, writes under the keys in §4; all JWT-only; list routes use page-number pagination with a total order ending in `id`):
  - `GET/POST /api/v1/news-posts` · `GET/PATCH/DELETE /api/v1/news-posts/{id}` · `POST …:publish` / `:unpublish` / `:archive` (all three need `website.news-post.publish`; create and edit use `.create` and `.update`; delete uses `.delete` and needs the post unpublished first).
  - `GET/POST /api/v1/school-events` · `GET/PATCH /api/v1/school-events/{id}` · `POST …:publish` / `:unpublish` / `:archive`. There is no DELETE, because §4 has no `website.school-event.delete` key: archive instead (the transitions use `website.school-event.publish`).
  - `GET/POST /api/v1/gallery-albums` · `GET/PATCH/DELETE /api/v1/gallery-albums/{id}` · `POST …:publish` / `:unpublish` (an album needs at least one item to publish, else 422 `empty_album`; delete needs it unpublished first and uses `website.gallery-album.delete`; there is no `:archive` route, which answers 404).
  - `GET/POST /api/v1/gallery-albums/{id}/gallery-items` · `PATCH/DELETE …/gallery-items/{item_id}` · `PATCH …/gallery-items:reorder` with `{ids: [...]}` listing every item of the album exactly once (the response is the ordered list of items). Item writes use `website.gallery-album.update`.
  - Slugs are one lowercase segment, 120 characters at most, unique per tenant among live rows. News `body` and event `description` are rich-text block documents; `video_embed` items need an `https` URL on `EMBED_HOSTS` (YouTube, Vimeo).
- Built in PR A: `GET/PATCH /api/v1/website-settings` · `GET /api/v1/navigation-menus` · `PATCH /api/v1/navigation-menus/{location}` (`header`, `footer_primary`, `footer_secondary`; at most 50 items, two levels, labels 1–60 characters) · `GET/PATCH /api/v1/seo-settings?target_type=&target_id=` (`site` takes no `target_id`; the target of any other type must be a live row of the tenant) · `GET /api/v1/themes` (active themes, with their section schemas). Every route above is JWT-only; `GET`s read under `website.page.view`, writes under the keys in §4; `:preview` needs `website.page.view` and returns a URL on the tenant's own host.
- Built in PR D: `GET/POST /api/v1/custom-domains` · `PATCH /api/v1/custom-domains/{id}` (writes only `is_primary`) · `POST /api/v1/custom-domains/{id}:verify` · `DELETE /api/v1/custom-domains/{id}`. The list reads under `AnyOf(website.custom-domain.create, .update)` (§4 has no view key); `POST` needs `.create`, `PATCH` and `:verify` need `.update`, `DELETE` needs `.delete`. Every row carries `dns_records`: the TXT record `_schoolhub-verify.<domain>` holding the token (`keep_after_verification: false`) and a direct CNAME to `WEBSITE_CNAME_TARGET` (`keep_after_verification: true`; CNAME chains are not followed). The dashboard renders the copy: keep the CNAME; the TXT record can be removed after verification, and if kept it must keep the token. Each row also carries `last_error_code` (`CustomDomainErrorCodeEnum`: `txt_missing`, `txt_mismatch`, `cname_missing`, `cname_mismatch`, `lookup_timeout`, `lookup_failed`, `domain_taken`, `target_unconfigured`; `null` when the last check passed, since the schema settings cannot express a blank enum member) beside the prose `last_error`. 422 reasons: `invalid_domain`, `platform_domain`, `duplicate_domain`, `domain_limit` (at most 5 live domains), `not_active` (primary needs an active domain), `tls_not_issued` (primary needs an issued certificate), `not_verifiable`. Input longer than `DOMAIN_INPUT_MAX_LENGTH` (317) is a 400 before any mapping. A domain another school holds answers `:verify` with 409 and `meta.reason` `domain_taken`. All JWT-only.
- Built in PR B: `GET /api/v1/contact-submissions` (filters: `status`, `created_at__gte`, `created_at__lte`, `created_at__lt` (exclusive, for a day range), `search`; page-number pagination) · `GET /api/v1/contact-submissions/{id}` · `PATCH /api/v1/contact-submissions/{id}` (writes only `status`: `new`, `read`, `responded`, `spam`; sets `handled_by` to the caller). `source_page_id` is null for a message sent with no page, and `handled_by_id` is null until someone triages it; the contract types both as nullable. Reads use `website.contact-submission.view`, the `PATCH` uses `.update`. The stored `ip` is never returned.
- **Public content API, built in PR C** (all under `/api/v1/public/`, `GET` unless stated; decisions in [ADR-0039](../decisions/0039-public-content-api.md)).
  - **Machine routes.** Every read below sends `Authorization: Bearer <machine token>` (the renderer's `WEBSITE_MACHINE_TOKENS`, scope `website.public-content.view`) and `?host=` (a school's subdomain or an active custom domain; the API resolves the school, the caller never asserts a tenant id). A staff JWT is refused with 401, and a machine token is refused with 401 on every CMS route. A missing or wrong token is 401, a write method is 405, and the rate is 1200/min per normalised host (429). A `tenant_id` parameter is ignored. Every read is a 404, the same one for each cause, when the host is unknown or its school is deleted, provisioning or deprovisioned, `module.website` is off, or the site is unpublished or in maintenance. `tenants/by-host` is the exception and reports instead.
  - **Cache headers.** Besides the file redirect, only `pages` and `site` set any: they always send `Vary: X-Preview-Token` and add `Cache-Control: no-store` when a preview token was used.

  | Route | Returns | Notes |
  | ----- | ------- | ----- |
  | `tenants/by-host?host=` | `PublicTenant`: `id`, `slug`, `name`, `status`, `website_status` (`live`, `maintenance`, `unpublished`), `branding` (`PublicBranding`), `locale` `{default_locale, enabled_locales, timezone, direction}`, `contact`, `custom_domain`, `enabled_modules` | 200 for a `live` or `suspended` school; 404 for an unknown host, a deleted tenant, provisioning or deprovisioned. Module off reports `unpublished`. For a school that is suspended, or whose site is not live, `contact`, `custom_domain` and `enabled_modules` are withheld (`null`, `null`, `[]`) |
  | `site?host=` | `PublicSite`: `theme` `{code, version, config}`, `navigation` `{header, footer_primary, footer_secondary}` of `{label, href, children}`, `header_config`, `footer_config`, `social_links`, `seo` | 404 unless live, or a valid preview token for this school (see below) |
  | `pages?host=&slug=` | `PublicPage`: `id`, `slug`, `path`, `title`, `page_type`, `status`, `is_homepage`, `published_at`, `updated_at`, `sections` (`{id, type, position, props}`), `seo` | An empty, missing or `/` slug is the homepage. 404 for an unpublished, archived or deleted page, and for `slug=home` |
  | `sitemap?host=` | A bare list of `PublicSitemapEntry` `{path, updated_at}` | Published, indexable pages (the homepage as `/`), news posts, events and albums |
  | `news-posts?host=&page_size=` · `news-posts/{slug}?host=` | `PublicNewsPost` list (newest first) · `PublicNewsPostDetail` | `page_size` is 1 to 50, default 50. A draft or archived post is 404 |
  | `school-events?host=&scope=&page_size=` · `school-events/{slug}?host=` | `PublicSchoolEvent` list · `PublicSchoolEventDetail` | `scope` is `upcoming` (the default, also the fallback for an unknown value) or `past`. A draft or archived event is 404 |
  | `gallery-albums?host=&page_size=` · `gallery-albums/{slug}?host=` · `gallery-items?host=&page_size=` | `PublicGalleryAlbum` list (with `item_count`) · `PublicGalleryAlbumDetail` (items, at most 100, plus `item_count`) · `PublicGalleryImage` list of the latest images across published albums | Albums order by `published_at` descending, nulls last |
  | `teachers` · `departments` · `classes` · `notices` `?host=` | `PublicTeacher`, `PublicDepartment`, `PublicClass`, `PublicNotice` lists | Opted-in records only (§20 "PR B: opt-in flags and `public.py`"); notices are published, unexpired and carry a plain-text body |
  | `files/{tenant_id}/{file_id}` | 302 to a presigned link | Anonymous (no token). 404 for every miss. `Cache-Control: public, max-age=300` |
  | `POST contact-submissions` | 201 `{status: "received"}` | Anonymous, see below |

  - **Preview.** `X-Preview-Token` (the signed token of `POST …/website-pages/{id}:preview`) is read from that header only; a query parameter is ignored. A bad, expired or other school's token is 404. With a token, `pages` reads that one page in any status (the `slug`, when sent, must match it; without one the token's page is returned) and `site` skips the "live" check. The operational-school and `module.website` checks still apply.
  - **Contact `POST`.** No machine token. Headers: `X-Tenant-Slug` (required), `Origin` (when present, its host must resolve to the same school, https only unless `DEBUG`), `Content-Type: application/json` (else 415) and an optional `Idempotency-Key` of at most 255 characters (longer is 422). The slug and `Origin` are checked before the body is read. The body is capped at 32 KB (413, declared or actual) and must be a JSON object (400). A filled honeypot `company_website` returns 201 and stores nothing. Rule failures are 422 keyed by field, an unknown slug, a foreign `Origin` or a site that is not live is 404, and throttles are 5/min per client IP and 200/hour per school (429). A retry with the same key and body replays the first response; the same key with another body is 422 `idempotency_key_reused`.
  - **CORS.** The allowlist adds a school's own origins (its subdomain and active custom domains) on `POST /api/v1/public/contact-submissions` only (the one route a browser calls); `Origin` hosts of suspended or unknown schools get no CORS headers.
  - Not built: `POST /api/v1/public/admission-forms` (waits for the admissions module; see [`deferred-work.md`](../deferred-work.md)).

### Built (PR C: public content API)

PR C adds machine auth, host resolution and the routes in §16. The rulings the contract rests on:

- **Machine auth and host.** `core/rbac/machine.py` holds `MachineTokenAuthentication`, `HasMachineScope` and `MachineClientThrottle`, set per view. `website_cms/hosts.py::resolve_host` matches exactly one label under `PLATFORM_DOMAIN` by slug (the apex, deeper names and `RESERVED_SUBDOMAIN_LABELS` resolve to nothing), else an active `custom_domain_routes` row of a live tenant. The host is lowercased, stripped of a port and trailing dot, and IDNA-encoded before any query.
- **Custom-domain tables.** `custom_domains` (RLS) and the platform-scope `custom_domain_routes` exist from PR C (migrations `0007` and `0008`); the route's tenant is tied to its domain's tenant by a composite foreign key in the database. PR D writes both.
- **Preview bypasses "live"**, for pages and for `site`, so a school can preview before its first publish. It does not bypass the operational-school or `module.website` checks.
- **`by-host` withholds** `contact`, `custom_domain` and `enabled_modules` for a school that is not `live` or whose site is not live.
- **The homepage answers at `/` only.** `home` is a reserved slug, a lookup by slug excludes the `home` page type, and the sitemap emits `/`. The renderer sends an empty slug for `/`. A pre-existing non-home page whose slug is `home` is still served at `/home` (deferred).
- **Branding is a whitelist.** `PublicBranding` emits exactly eleven keys; each value must match a pattern (hex, `rgb()`, `hsl()` or `oklch()` colours, a font list, a safe URL, a CSS length) or it is `null`, so tenant branding cannot inject CSS.
- **Navigation drops** an unpublished, archived or deleted page target together with its children.
- **All-day events** are compared by the school's local day (`Tenant.local_date`), so an all-day event stays `upcoming` until its local day ends; timed events compare `coalesce(ends_at, starts_at)` with now.
- **Albums** hold at most 100 items (`GALLERY_ALBUM_ITEMS_MAX`; adding one more is a 422 `too_many_items`), and the public detail returns all of them (`PUBLIC_ALBUM_ITEMS_MAX` is the same constant) with an `item_count`.
- **An unpublished file stays reachable** for up to about 65 minutes through a link already issued: the 302 is cached 300 s and the presigned link lives 3600 s. Revoking a file does not recall a link a visitor holds.
- **`NUM_PROXIES` is required in production** (and as the required `num_proxies` variable in the production and staging Terraform; operators set the real hop count). Per-IP throttles (`public_form`, `public_file`, the auth throttles) and the stored contact and audit IPs depend on it: a wrong count lets a client rotate `X-Forwarded-For` to escape a limit or records a proxy's address. `core.api.client_ip.client_ip` is the one derivation.
- **Idempotency.** The renderer must send a random `Idempotency-Key` per submission: the key is scoped to the school and endpoint, so a guessable key lets a later visitor replay an earlier visitor's response.
- **CORS receiver.** `website_cms/cors.py` allows only the contact route and answers from `resolve_host`, caches each host's answer for 60 s, hashes the host in the cache key and fails closed on any database or cache error. `CORS_ALLOW_CREDENTIALS` is global, so an allowed tenant origin also receives `Access-Control-Allow-Credentials`; the route is anonymous and bearer-less, so that carries no authority.
- **Flag signal.** A tenant override of `module.website` queues revalidation of every host tag; a change of the flag's platform default does not (deferred).

Detail sheets render the blocks as plain elements (`rich-text-view.tsx`), never `dangerouslySetInnerHTML`, and name an unknown block type instead of hiding it |
| Cover images | News, events and albums take a cover through `ImageFileField` (upload, then the file id), inside an `UploadTrackerProvider` so Save is held while a file is uploading. No cover is an omitted key on create and `null` on edit, which clears it. The API returns only file ids, so there is no thumbnail (see `deferred-work.md`) |

An all-day event's days are sent as local midnight; `ends_at` is `null` only when no end is given. A client check refuses an end before the start, and the server's `end_before_start` shows under Ends. **Limit:** every wall-clock value, and an all-day event's day, is read and shown in the browser's time zone, because the dashboard does not yet know the school's zone (`lib/date-time-input.ts`); an event entered from another zone shifts by the difference. Tracked in `deferred-work.md` |
| Gallery: items | The album page lists its items in a grid. Reorder is drag and drop (`@dnd-kit/sortable`, pointer and keyboard sensors, translated announcements) or the Move earlier and Move later buttons; each reorder sends the whole id order (`PATCH …/gallery-items:reorder`), shows the new order at once and is replaced by the server's answer, and a refusal restores the previous order with its reason (`invalid_item_ids`). Moves are held while the list is fetching or a reorder or upload is running |
| Gallery: uploads and video | Multi-upload sends files one after another in pick order with progress (`Services.files.uploadFile(file, "website.media")`, then `createGalleryItem`); a failure is listed by file name with its own reason and the rest still land. The batch finishes even if the person navigates away, then invalidates the website queries; a failure in a batch left behind is reported in a toast naming the files. Upload photos and Add video are held during a reorder. Add video takes a link, caption and description; the dashboard checks only that the link is present, `https://` and at most 500 characters, and leaves the YouTube and Vimeo allow-list to the server so the two cannot drift (`embed_host_not_allowed`, `invalid_url` show under the link). Item writes use `website.gallery-album.update` |
| Alt text | The server accepts an empty `alt_text` (`item_services.py::_validate_item`); the dashboard requires a description when a photo's edit is saved. A photo added by upload starts without one (a filename is a poor description) and its tile shows "Needs a description" until one is added. The rule is therefore enforced only here; a server 422 is deferred |
| Refusal messages | One helper for every website screen: `shared/reason-message.ts` (`reasonText`, `withReasonText`) turns the API's `"<reason>: <sentence>"` detail into `website.reasons.<reason>` in the viewer's language, and an unknown reason keeps the server's own sentence. ### Built (dashboard): PR H

PR H adds the site-wide screens to the dashboard Website area, stacked on PR G and on the custom domains API (PR D). The code is in `apps/dashboard/src/features/website/{settings,navigation,seo,domains,inbox}/`.

| Area | State |
| ---- | ----- |
| Routes and menu | `/website/settings`, `/website/navigation`, `/website/seo`, `/website/domains` and `/website/inbox`. `website-sections.ts` gates each section on its own key (decision 12a): Navigation on `website.navigation.update`, Settings on `website.settings.update`, SEO on `website.seo.update`, Domains on either `website.custom-domain.create` or `.update` (the keys the list reads under; §4 has no view key) and Contact inbox on `website.contact-submission.view`. The group shows when any section is visible, so `reception` sees only the inbox and `school_owner` only Domains (`menu-config.test.ts`). The settings, navigation and SEO reads need `website.page.view`, which every seeded role offered them holds; `WebsiteReadGate` (`shared/website-read-gate.tsx`) mounts those screens only with it, and a custom role holding just an update key sees a translated explanation instead of a 403 |
| Site settings | A status card (a Live, Maintenance or Offline badge) whose Published and Maintenance mode switches never flip directly: each opens a confirm and only then sends that one field. The home page is shown, linking to its editor, not chosen. The form holds the theme (choosing another resets `theme_config`), the theme's own settings through `SchemaFields`, social links (https or a site path) and the analytics id; a 422 at `theme_config.*` lands under its input. Before the first save (`exists: false`) the button reads "Create the website". `header_config` and `footer_config` have no editor |
| Navigation | One tab per menu (header, footer, footer second row), each mounted while hidden so unsaved edits survive a look at another, with its own Save. Links reorder by drag (pointer and keyboard, translated announcements) or move buttons; a link nests under the one above and a sub-link moves back out, two levels deep, at most 50 links. Removing a link with sub-links is confirmed. The page picker reads every published page; a stored target that is no longer published is marked and kept until another page is chosen. The server's single `invalid_target` reason is worded by the link's type |
| SEO | An "SEO" action (with `website.seo.update`) in the page, news, event and album editors opens `SeoDialog`; a tab would unmount the page editor's unsaved sections, and the news and event editors are themselves dialogs. `/website/seo` shows the site's row inline. Title, description, share image (uploaded through `ImageFileField`) and canonical link (https or a site path); `structured_data` has no input |
| Custom domains | One card per domain: status, HTTPS and Primary badges; what the last DNS check found (`last_error_code` in the viewer's language, the server's `last_error` as the fallback); and the records to add, each name and value with a copy button. The note under each record follows `keep_after_verification`: keep the CNAME; the TXT can be removed after verification, and if kept must keep its value; a CNAME must point straight at the target, as chains aren't followed. Check DNS shows for a pending, checking or failed domain; a failed check is a 200 the card reads, and an inconclusive one keeps the status. **No domain can be primary until its certificate is issued**: Make primary stays disabled with the reason while the domain isn't active or its TLS is `pending`, which in v1 (null edge provisioner) is always. Remove is confirmed. Adding a domain checks only that one was entered, then shows its DNS records; the server decides validity, and every 422 (`invalid_domain`, `platform_domain`, `duplicate_domain`, `domain_limit`, `not_active`, `tls_not_issued`, `not_verifiable`) and the 409 `domain_taken` show in the viewer's language (`website.reasons.domains.*`). A 409 is also stored as the claim's `last_error_code`, so the card matches the two by `meta.reason` and says it once. Add is held at five domains |
| Contact inbox | A directory of the website's contact messages, newest first, with search, status and a received-date range in the URL (ADR-0024); the local days go to the API as instants: `from`'s midnight to `created_at__gte` and the midnight after `to` to `created_at__lt` (`localDateToIso`, `nextLocalDayToIso`). A new message's sender is bold. A sender opens the message in a sheet (email and phone as links, the message as sent); opening changes nothing. With `website.contact-submission.update`, Mark read, Mark responded and Mark as spam save the status, and a refusal shows in the sheet. The stored IP is never returned |
| Tests | Jest for each screen (`site-settings`, `navigation-editor`, `navigation-model`, `seo-form`, `custom-domains`, `contact-inbox`), the services and `menu-config`; mocked Playwright `e2e/tests/dashboard/website-site.spec.ts` on `e2e/src/mocks/domains/website-site.ts` (typed from the generated schema, each role holding exactly its seeded keys), including a mouse drag of a sub-link that must not move its parent |
| Known limits | Some settings 422s carry no reason prefix, so an Urdu viewer sees the server's English. The domain limit is declared in three places. There is no control to unset the primary domain. See [`deferred-work.md`](../deferred-work.md) "PR H follow-ups" |
