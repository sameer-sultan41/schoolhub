  `--frozen-lockfile`. Nothing was installed, built, linted, or tested locally — CI is the
  source of truth.
- **No module screens.** Only the dashboard home + auth/shell exist. Students, fees,
  attendance, academics, timetable, examinations, communication, parent-portal, … are
  untouched — this is the biggest gap against `docs/01-phases/phase-2-core-build.md` tier 1+.
  `apps/api` only has the `school_organization` Django app; nothing downstream of it exists
  on the backend either, so there is no API to build most module screens against yet.
- **`e2e`'s `live` project is opt-in only** — it needs the real docker-compose stack and does
  not run in the PR gate; only the mocked `dashboard`/`website` projects do.

## Start here next session

1. **CI is fully green** — lint, typecheck, tests, both app builds, Playwright E2E
   (mocked projects), and the gitleaks scan. Keep it that way; it is the source of truth
   for pass/fail.
2. **Leave the two-TypeScript setup alone.** `typescript` is aliased to the TS 6 API for
   tooling and `@typescript/native` supplies TS 7's `tsc` — the arrangement the TypeScript 7
   release notes prescribe, because 7.0 ships no stable programmatic API. Pointing
   `typescript` at 7.x kills the whole lint layer and Next's type checking. Collapse to one
   TypeScript only after typescript-eslint supports the 7.1 API (#10940).
3. **Do not bump ESLint to 10.** It removes `context.getFilename()`, which
   `eslint-plugin-react` (bundled in `eslint-config-next`) still calls; every app lint task
   dies. Wait for an ESLint 10-compatible `eslint-plugin-react`.
4. **Decide the typed-routes question.** App code uses explicit prop types rather than Next 16's
   generated `PageProps`/`LayoutProps` globals, so `tsc --noEmit` works without a prior build.
   If the team prefers the generated globals, add `next typegen` to the `typecheck` script.
5. **Backend needs to grow past `school_organization`** before the next frontend module
   screen can be built against real endpoints — student-management and staff-management are
   next per the tier-1 build order in `docs/01-phases/phase-2-core-build.md`.
6. **Then build the first module screen** end-to-end (students list is the natural first) using
   `queryKeys.list()`, the shadcn `DataTable`, and `<Can>` — it will prove the whole stack.

## Conventions worth re-reading before writing code

- Components resolve colour through `--sh-*` custom properties only — no literal hex, no
  `blue-600`. Tenant branding is the only thing that may override a `--sh-color-*`/
  `--sh-font-*`/`--sh-radius` value at runtime (still true, still enforced the same way);
  the *default* those tokens resolve to when no tenant override is present is now
  SchoolHub's own "Navy & Gold" platform brand, not neutral grey — see the doc
  comment at the top of `packages/ui/src/styles/theme.css`. A `--sh-platform-*` tier is
  separate and never tenant-overridable at all: it skins chrome that isn't any tenant's
  (`/login`, the platform-landing page, the unknown-host page).
- Permission-aware UI is UX, never enforcement.
- `apps/website` must never gain a write path.
- Every new env var goes into `.env.example` with a dummy value and a comment.
